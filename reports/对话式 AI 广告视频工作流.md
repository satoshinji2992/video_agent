# 广告视频 Agent 赢在编排，不在模型

到 2026 年 10 月，凡是"聊几句就出一条 30 秒广告"的产品，底层做法基本一致：一个 LLM 充当制片人，先把需求变成带秒数的分镜，再逐镜头分派。文字、价格、Logo、CTA、字幕这类必须精确的内容用代码渲染，真人、场景、产品使用画面这类必须逼真的内容交给 Seedance、可灵、Veo 等生成模型，最后用 FFmpeg 合成，再经过一轮视觉自检。模型大家都在用同一批，Seedance 同时出现在 TopView、Pexo、invideo、Creatify 和 HeyGen 里，所以产品之间的差距出在编排层上：分镜能不能单独修改、镜头能不能局部重渲染、对话会不会把工作推回给用户。对话体验方面，项目对标的 Grok Bot 其实不做视频。它让人觉得"像在跟真人发消息"，靠的是一套交互约定：简短确认，然后安静地干活，只在需要审批或者成片出来时回来。模型文笔在这里起的作用不大。项目原先那个 vibe-coded 应用"表格加选项"的 AI 味，最可能的原因是走 API 时缺了 claude.ai 那份"短句、散文、一次最多问一个问题"的系统提示词，模型本身能力不是主因。对我们的 3 天 demo 来说，这意味着及格线可以达到，只要把精力放在三件事上：可局部修改的 `project.json` 分镜、按镜头路由的双渲染路径、一份认真写的对话层提示词加进度卡片。

## 各家都在做"制片人加分镜"，只是交互外壳不同

**xAI 有两个产品，常被混为一谈。** Grok Imagine Agent Mode 在 2026 年 4 月 30 日前后以 beta 形式上线网页端，xAI 没有发正式博客或文档（[TestingCatalog](https://www.testingcatalog.com/xai-debuts-imagine-agent-in-grok-with-open-canvas-ai-workspace/)）。它把对话搬到一张无限画布上：一个简报进来，agent 依次铺出"规划、生成候选图、挑最佳、图生视频、拼接、导出"等节点，每个节点都能单独重新提示或分叉做 A/B，比如"把第 2 场改成黄金时刻光线"（[Codersera](https://codersera.com/blog/grok-imagine-agent-mode-launch-2026/)）。上线时单段只有约 6 秒、720p，所以任何 30 秒成片都必然是多镜头拼接，第三方指南直说"想要一个连续 30 秒的镜头，Agent Mode 还不行"。底层模型在 7 月 31 日获得官方多参考能力，每张参考图"锁定一样东西：一张脸、一个产品、一个地点"（[x.ai](https://x.ai/news/grok-imagine-video-1-5-references)）。API 的编辑接口只接受 8.7 秒以内、720p 以下的源视频（[docs.x.ai](https://docs.x.ai/developers/model-capabilities/video/overview)），所以对生成视频而言，"重新生成整个镜头"仍是主要的修改手段。另一个产品 **Grok Bot**（8 月 11 日 beta）是"一直在线的 AI 队友"，发布页从头到尾没有提到 Imagine 或视频生成（[x.ai](https://x.ai/news/introducing-grok-bot)）。项目看重的是 Grok Bot 的对话感，可它展示的是交互模式，并不是一个视频产品。

**Anthropic 这边的"Opus 5.5 视频"全部是代码。** Opus 5.5 的发布公告里没有出现视频、动画或动效（[Anthropic](https://www.anthropic.com/news/claude-opus-5-5)）。社区里刷屏的作品，是模型在 Claude Code 里写出 HTML、Canvas、Three.js 或 Remotion 场景，每一帧都是时间的纯函数，由无头浏览器逐帧截图，再交给 ffmpeg 编码成 MP4（[opus5video](https://opus5video.com/how-to-make-videos-with-claude/)）。实践者总结出的规律是"提示词只占视频的 10%"，其余靠工作框架：先确认带时间码的分镜和每镜一张静帧再写代码；把渲染约定（`seek(t)`、禁用 `Math.random` 和计时器）、禁用的"AI 感"套路（渐变上居中标题、角标、假时间码）写进 CLAUDE.md；让 Opus 看自己渲染出的联系表，按 1 到 10 分打分，挑出带时间戳的三个最差问题，并且"只重渲受影响的那几秒"（[Movez](https://movez.substack.com/p/how-to-build-motion-design-studio)）。有个细节值得注意：Opus 默认会跳过 Remotion 或 HyperFrames，自己手写渲染引擎，除非你明确点名框架（[Movez](https://movez.substack.com/p/how-to-build-motion-design-studio)）。10 月 8 日上线的 **Claude Motion** 把这条纯代码路线做成了产品，官方说法是"没有任何视频模型参与，所以你可以改任何一个字、数字或时间点，然后导出 MP4"（[@claudeai](https://x.com/claudeai/status/2108271558170976743)）。帮助中心也写明它不能生成逼真画面或真人（[Claude Help Center](https://support.claude.com/en/articles/17454997-get-started-with-claude-motion)），时长和分辨率上限都没有公开。真实画面要靠 MCP 接入，比如 OpenArt 连接器，其推荐用法是"先给我看分镜，再生成第 1 个镜头"，这样在花积分之前就能先改方案（[OpenArt](https://openart.ai/blog/how-to-generate-images-and-videos-with-claude-opus-5-5/)）。

**Seedance 是这一代广告 agent 的公共底座。** 目前的旗舰 Seedance 2.5 支持 4 到 30 秒"连贯直出"，最高 1080p，原生生成立体声音画，可以带最多 30 张参考图、10 段参考视频和 10 段参考音频，同一个模型还能做编辑和延长（[火山方舟创建任务文档](https://www.volcengine.com/docs/ark/create-video-generation-task-api)）。官方示例本身就是一条 15 秒的饼干广告：一段提示词里写了开场、特写、慢动作高潮和带英文标语的结尾，每个节拍用 `@图像1`、`@视频N` 绑定到参考素材上。2.0 系列上限 15 秒，1.0 系列 2 到 12 秒，所有模型都是 24 fps（[火山方舟教程](https://www.volcengine.com/docs/ark/video-generation-tutorial)）。

**国内产品已经把"一句话出片"和"爆款复刻"做成消费级功能。** 字节的小云雀把素材和口播稿变成一份带精确时长的营销分镜：开场吸引 3.2 秒，产品展示 6.2 秒，口碑验证 6.6 秒，渠道保障 5 秒，个人推荐 3.2 秒，行动号召 3.8 秒，合计约 28 秒（[腾讯新闻](https://view.inews.qq.com/a/20251201A02WSS00)）。执行界面分成理解分析、创意策略、剪辑成片三段，每段都有"修改"按钮（[新榜](https://zhuanlan.zhihu.com/p/1981928675839603394)）。10 月 28 日字节把小云雀并入即梦/Dreamina（[KrASIA](https://kr-asia.com/bytedance-folds-xiaoyunque-into-dreamina-as-it-consolidates-ai-apps)）。可灵的灵动画布 Agent 模式提供一键分镜、多视角扩展、电商组图和多轮对话编辑（[搜狐/AITOP100](https://www.sohu.com/a/981977307_122496371)）。阿里妈妈的万相妙应 Agent 2.0 一句"给我的连衣裙做一套种草素材"就能产出图片、视频和标题，还会记住"800×800、室内场景、职场女性"这类偏好（[淘宝教育](https://daxue.taobao.com/information/detail.jhtml?id=1537)）。Vidu Agent 主打"选场景、传产品图、说一句话"，产出 15 到 30 秒带配音的成片（[知乎](https://zhuanlan.zhihu.com/p/1988984388596307822)）。MiniMax 的 Media Agent 用一条 30 秒玉米片广告做展示（[MiniMax](https://www.minimax.io/news/minimax-hailuo-23)）。

**海外广告 agent 的分化主要在入口和修改粒度上。** TopView 自我定位为"告诉你的 Agent 就行"：它规划场景、为每一步挑模型、生成素材，并且"让每个镜头都能在 Canvas 上编辑"，视频用 Seedance 2.0，图片用 GPT Image 2（[TopView](https://www.topview.ai/)）。Creatify Agent 从一个商家 URL 生成 5 场景广告，厂商宣称约 60 秒出片（[Creatify](https://creatify.ai/blog/i-turned-one-url-into-a-5-scene-converting-ad-in-60-seconds-creatify-agent)）。它公开的技术报告最有参考价值：Producer 产出一张带类型的"素材图"（产品事实、人设、品牌状态、必须出现的屏幕文字），这张图同时是生成规格和视觉评审的评分标准，没通过的场景单独重生成，不会整条重来（[Creatify 技术报告](https://d35ghwdno3nak3.cloudfront.net/videoadagent_bench/v1/research-creatify-agent.html)）。Arcads 走表单路线，写脚本、选数字人演员，就得到一条口播 UGC，一次测试中每条约 7 到 8 分钟（[Predis.ai](https://predis.ai/review/arcads/)）。HeyGen Video Agent 的 API 有 `generate`（一次出片）和 `chat`（"暂停等你审阅并支持修改"）两种模式，图形部分用它开源的 HTML 转视频框架 HyperFrames 渲染，字幕作为单独文件 `subtitle_url` 返回（[HeyGen API](https://developers.heygen.com/docs/video-agent)）。Pexo 是纯对话 agent，流程是规划、分镜、成片，修改方式是"像在 Google Doc 里评论一样标出要改的地方"（[Pexo](https://pexo.ai/)）。它还以 Claude Code skill 形式发布，宣称 15 秒、3 镜头的产品广告 8 分钟内出片（[skillselion](https://skillselion.com/skills/pexoai/pexo-skills/video-ad)）。Higgsfield 是反例：改视频就等于重新生成（[aliteq](https://aliteq.com/higgsfield-ugc-ads)）。

把这些产品放在一起看，有两条共同规律。一是**先给计划，再花钱**：小云雀的三段式、HeyGen 的 `chat` 模式、Pexo 的计划审阅、OpenArt 的"先看分镜"都是这个思路。二是**广告时长受制于单次生成上限**：Seedance 2.0 是 15 秒，Higgsfield 是 12 或 15 秒，腾讯云的 `CloneViral` 是 4 到 15 秒，所以 30 秒广告通常需要编排层把多个镜头拼起来，并负责镜头之间的连贯。

## 爆款克隆复制的是"骨"，不是"皮"

各家"爆款复刻"的技术可以归成两种，常常混用。第一种是**蓝图克隆**：多模态模型把参考视频拆成结构化分镜，包括前 3 秒钩子、节拍时长、景别与运镜、转场、字幕样式、音乐卡点和口播稿，然后为新产品改写，所有镜头都重新生成。新榜对小云雀的描述是"模仿的不是爆款内容的'皮'而是'骨'"，抽取的"爆款DNA"包含主题、结构、文案节奏和视觉风格（[新榜](https://zhuanlan.zhihu.com/p/1981928675839603394)）。第二种是**以参考视频为条件重新生成**：参考片直接作为视频模型的输入（视频转视频、运镜或动作控制、Seedance 式的多模态参考），产品图作为主体参考，运镜、动作、节奏和色调保留下来，只换掉商品。录咖、WeShop 和腾讯云的 `CloneViral` API 都属于这一类，`CloneViral` 的最小请求就是 `VideoUrl` 加 `Product.Images[]`，异步返回 TaskId（[腾讯云](https://cloud.tencent.com/document/api/862/135033)）。TopView 公开的模板提示词把边界说得很清楚：节奏、镜头韵律、字幕和钩子结构跟随参考视频，广告中的商品换成用户的产品图（[TopView 案例](https://www.topview.ai/zh/featured-cases/clone-viral-product-ad)）。

对我们来说有一个硬约束：**Claude 看不了视频**。它只接受 JPEG、PNG、GIF、WebP，动图也只读第一帧（[Claude 视觉文档](https://platform.claude.com/docs/en/build-with-claude/vision)）。所以"看懂"参考片必须先做确定性拆解：用 PySceneDetect 或 FFmpeg 的 `select='gt(scene,0.4)'` 切镜头，每个镜头抽几张静帧拼成联系表，用 faster-whisper 拿到逐词时间戳，再测出 BPM 和节拍点，最后交给 Claude 看图，输出固定 schema 的 JSON（[PySceneDetect](https://www.scenedetect.com/docs/latest/cli.html)，[faster-whisper](https://github.com/SYSTRAN/faster-whisper)）。HyperFrames 的实测经验可以直接借用：把参考片逐帧写成带时间戳、带绝对数值的描述，一次就能复现约 75%；迭代时要用绝对目标（"圆点半径等于行距的 25%"），不要说"再细一倍"，因为"相对修正会来回摆"；仅凭文字最多做到约 90%（[HyperFrames](https://hyperframes.heygen.com/prompting/recreating-references.md)）。版权方面整个行业的保护都很薄。Higgsfield 只要求用户声明对参考广告有权利，WeShop 建议只复刻结构、动作或创意风格（[WeShop](https://www.weshop.ai/zh-Hans/apps/video-replication)），我们没有找到任何一家做自动相似度或 IP 检测。

## 业界流水线是十几步的确定性装配线，LLM 只负责其中的判断

把 Creatify、ViMax、product-film-skill、HyperFrames 等真实系统的阶段合起来，可以得到一条相当稳定的流水线：简报和品牌素材摄入，提炼卖点，写钩子、脚本和节拍表，排出带时长的镜头表，生成关键帧静图并确认，再逐镜头出运动画面（代码渲染或图生视频），然后是带时间戳的 TTS、带节拍网格和闪避处理的音乐、逐词对齐的字幕、在无头 Chrome 或 FFmpeg 里的确定性装配、分层自动质检，最后按参数批量出变体。ViMax 的消融实验说明了"先关键帧、后视频"这个顺序的价值：去掉镜头之间的依赖关系，全局一致性下降 8.7%；用视觉模型从 2 个候选里挑一个已经足够，挑 3 个或 4 个不再有提升（[ViMax](https://arxiv.org/html/2606.07649v1)）。编排层的价值也有数据支撑，尽管来自厂商自测：在 Creatify 的基准上，Seedance 2.0、可灵 3.0、Veo 3.1 直接生成多场景广告，幻觉分分别是 3.65、3.80、3.85，都超过了 3.0 的不合格线，而加上 agent 编排后降到 1.90（[Creatify 技术报告](https://d35ghwdno3nak3.cloudfront.net/videoadagent_bench/v1/research-creatify-agent.html)）。

**项目状态应该是一份结构化文档，聊天记录只是它的修改日志。** 各家能做到"只改一处"，靠的都是同一个结构：Grok 画布的节点、Claude Motion 的"改一个字其余不动"、Movez 的"只重渲受影响的秒数"、小云雀对单个关键帧的重生成，底层都是一份可以局部失效的分镜。具体做法是用一份 `project.json` 记录画幅、时长、镜头数组、叠加文字、口播分句、音乐和字幕样式，每个生成素材都用参数哈希做内容寻址。用户说"把第 3 镜换成户外"，只有那个镜头的哈希变了，其余素材从缓存复用，重新拼接只需要几秒 FFmpeg。改字幕则完全不涉及生成调用。HyperFrames 已经提供了现成的轮次级历史记录（`history begin/end --who claude`，以及只撤销该 agent 最近一轮的 `undo`）和时间线编辑命令（[HyperFrames CLI](https://hyperframes.heygen.com/packages/cli.md)）。

**让口播决定时长。** 先生成 TTS，量出每句话的实际长度，再据此定镜头时长，不要用估算的语速。生成模型的时长是离散的（Seedance 只接受 4 到 15 秒或 4 到 30 秒的整数秒），所以略多生成一点，装配时再裁。中文字幕没有空格，需要按字分组。ElevenLabs 返回的是字符级时间戳，正好适合中文切分（[ElevenLabs](https://elevenlabs.io/docs/api-reference/text-to-speech/convert-with-timestamps)）。

**Seedance API 有几处工程细节会直接影响 demo。** 国内用火山方舟，海外用 BytePlus，两边接口一样：`POST {base}/contents/generations/tasks` 返回 `cgt-…` 任务 ID，之后轮询或接收 `callback_url`，鉴权只支持 API Key（[BytePlus](https://docs.byteplus.com/en/docs/modelark/create-video-generation-task-api)）。BytePlus 端 2.5 的模型 ID 是 `dreamina-seedance-2-5-260628`，火山端是 `doubao-seedance-2-5-260628`。2.5 的 `duration` 默认值是 -1，意思是由模型自己决定时长，而费用按时长计，所以每次都要显式指定。结果 URL **24 小时过期，2.5 的链接最多只能下载 100 次**，必须立刻转存（[火山方舟查询文档](https://www.volcengine.com/docs/ark/get-video-generation-task-api)）。首帧模式、首尾帧模式和全模态参考模式不能在一个请求里混用。2.5 的 1080p 输出是 10-bit HEVC，浏览器播放前需要转成 8-bit H.264。**带真人脸的参考图或视频会被拒**，只能用官方虚拟人像库、经过授权的真人素材，或者同账号 30 天内由 Seedance 生成的人脸视频（[火山方舟创建任务文档](https://www.volcengine.com/docs/ark/create-video-generation-task-api)）。并发是最容易被忽略的瓶颈。2026 年 5 月的快照显示 2.0 系列个人账号只能同时跑 3 个任务、企业账号 10 个（[模型列表快照](https://www.volcengine.com/docs/82379/1330310)）。10 个用户同时在线时，没有队列一定会撞上 429。另外，BytePlus 的视频服务据报道不对美国开放，各来源说法有冲突，官方条款我们没能读到（[TechJack Solutions](https://techjacksolutions.com/?p=71940)）。

时间和成本可以粗略估算。官方查询示例里，2.0 生成 5 秒 720p 用了 56 秒（[火山方舟查询文档](https://www.volcengine.com/docs/ark/get-video-generation-task-api)）。官方 Python 示例每 10 秒轮询一次，30 分钟后放弃。3 月份即梦消费端高峰期出现过 10 秒视频排队 6 到 8 小时的情况（[36Kr](https://m.36kr.com/p/3718471239038593)），API 有没有排队 SLA 不清楚，必须实测。价格方面，两份官方示例的 token 数都符合"宽×高×(24×秒数+1)/1024"这个式子，这是我们根据示例反推的规律，并非官方公布的公式。照此计算，按二手渠道报价，2.5 生成 30 秒 720p 约 ¥45 或 $6.9（火山价 [Leadde](https://leadde.ai/blog/how-much-is-seedance-2-5)，BytePlus 价 [CometAPI](https://www.cometapi.com/seedance-2-5-api-pricing/)）。官方的样片模式先出 480p，再用样片 ID 出终版；在"重抽 4 次"的情形下，官方测算可省 57% 成本，速度接近两倍（[搜狐](https://www.sohu.com/a/1079574815_122066678)）。

## 路由只问一个问题：这个镜头必须精确，还是必须逼真

Agent 自主选择渲染路径的判断标准很简单。**凡是承载文字、数字、界面、价格、Logo、法律声明和字幕的镜头，走代码。** 原因在于生成模型会让屏幕文字变形、字母漂移、Logo 走样：扩散模型逐帧挪动像素，并不知道某一团像素是商标，而且"没有任何厂商公布过任何视频模型的 Logo 保真成功率"（[laozhang.ai](https://blog.laozhang.ai/en/posts/fix-logo-distortion-ai-product-video.md)，厂商博客）。代码镜头渲染结果是确定的，改一个字的边际成本接近零，每次重渲都完全一致，Claude Motion 坚持不用视频模型也是出于这个理由。**真人、地点、产品被使用的场景、穿过真实空间的运镜，走生成模型。** 绝大多数广告应该是**混合**的：生成的空镜画面不带任何文字，代码叠加文字层，结尾品牌卡永远用代码做。生成镜头的提示词里写明"无文字、无 Logo、无招牌"，并且给叠加层留出空白区域。

升级规则也要定下来：默认走代码，只有简报确实需要代码做不出的真实感时，才把某个镜头升级为生成镜头；每个生成镜头最多抽 2 次（ViMax 的数据显示 best-of-2 已经够用）；仍然没有通过产品或 Logo 质检时，退回代码，用真实产品照片加推拉、扫光这类 2.5D 运动。产品主图是最容易出问题的地方。厂商经验是先确认一张正面或略带三分之四角度的静图，旋转不超过 15 度，用光线、蒸汽或镜头运动来制造动感，不要让产品自己转起来（[laozhang.ai](https://blog.laozhang.ai/en/posts/fix-logo-distortion-ai-product-video.md)）。Seedance 拒收真人脸参考，这又给路由加了一条：用户上传带真人的照片时，要么改用虚拟人像，要么只拍手部或只拍产品。

渲染工具方面，用户指定的"HTML/canvas、无头 Chrome、FFmpeg"恰好就是 HyperFrames 的架构。它采用 Apache-2.0 协议，在无头 Chrome 里逐帧 seek，再交给 FFmpeg 编码，确定性约定是 `time = floor(frame)/fps`，禁用 `Date.now()`、`requestAnimationFrame` 和未设种子的随机数（[HyperFrames 确定性](https://hyperframes.heygen.com/concepts/determinism.md)）。它还附带 lint、浏览器布局检查、联系表快照、本地 Kokoro TTS（包含普通话音色）和节拍检测，命令都支持 `--json`，适合 agent 调用（[HyperFrames CLI](https://hyperframes.heygen.com/packages/cli.md)）。HeyGen 自己做过一次对比（只跑了一次）：同一段需求交给 Opus 5.5，用 HyperFrames 11 分 50 秒出片，没有往项目里装任何依赖；用 Remotion 12 分 30 秒，装了约 950 MB 的 `node_modules`（[HyperFrames vs Remotion](https://hyperframes.heygen.com/guides/hyperframes-vs-remotion.md)）。Remotion 对超过 3 人的公司收费，服务端调用 `renderMedia()` 算"自动化"用途，每月至少 $100（[Remotion 许可 FAQ](https://www.remotion.dev/docs/license/faq)）。

## 自然的对话感来自一套交互约定和系统提示词

Grok Bot 的交互约定可以概括成一句话：你像给同事发消息一样交代任务，它在自己的云端电脑上把活干完，"只在需要你批准时回来"（[x.ai](https://x.ai/news/introducing-grok-bot)）。DevRel 指南补充了它的完成方式：干完之后"发截图或一段视频"（[Grok Bot 101](https://x.ai/bot/guides/grok-bot-101)）。评测者 Ben Tossell 把这种感觉归因于"少即是多"：功能和 Codex、Claude 差不多，只是少了几步（[Ben's Bites](https://www.bensbites.com/p/grok-bot-is-not-what-you-think)）。列表格让用户选的交互之所以有 AI 味，是因为它在第二步就把活推回给了用户，违背了"安静干活"这个约定。

我们的应用听起来像机器人，最主要的原因很可能有据可查。claude.ai 给 Opus 5.5 的系统提示词要求：一次最多问一个问题，并且先尝试回答再澄清；尽量少用粗体、标题和列表；日常对话用散文，可以很短（[Opus 5.5 系统提示词](https://platform.claude.com/docs/en/release-notes/system-prompts/claude-opus-5-5)）。但 Anthropic 明确说明**这些系统提示词不适用于 API**（[系统提示词总览](https://platform.claude.com/docs/en/release-notes/system-prompts/overview)）。Agent SDK 不设 `systemPrompt` 时只有一份只讲工具调用的最小提示词，而 `claude_code` 预设大部分内容是编码指导；官方建议聊天界面这类"不同外观"的 agent 自己写提示词（[Agent SDK 文档](https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts)）。有几个因素会叠加上去。提示词本身如果用 Markdown 标题和表格写，输出也会偏向 Markdown（[提示词最佳实践](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)）。Anthropic 点名 Opus 5.5 的一个毛病，是在回合结尾列出一串其实并不阻塞工作的决策让用户选；建议的做法是直接给出自己的推荐，然后继续做不依赖答案的部分（[Prompting Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)）。还有一点，effort 参数只控制想多少，不控制说多少，回复长短只能靠提示词和示例来管（[Prompting Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)）。

真正需要用户拍板的时候，有一个四级阶梯可以用。可逆又便宜的选择（配乐、字体、节奏、调色）由 agent 自己决定，用半句话告诉用户选了什么。会实质改变产出的选择（9:16 还是 16:9，15 秒还是 30 秒）问一个问题，问题里带上推荐，同时把不依赖答案的工作先做起来。偏视觉、看品味的选择用 Agent SDK 的 `AskUserQuestion` 弹卡片，2 到 4 个选项，可以附 HTML 预览图，并保留"其他"让用户自由填写（[Agent SDK 用户输入](https://code.claude.com/docs/en/agent-sdk/user-input)）。昂贵或不可逆的操作放在便宜的预览后面做审批关口。需要注意，`AskUserQuestion` 在子 agent 里不能用，所以所有面向用户的选择都必须由主线程的"制片人"来发起。

长任务的节奏同样影响观感。OpenClaw 的默认做法可以直接照搬：气泡之间随机停顿 0.8 到 2.5 秒，消息一到立即显示"正在输入"，进度放在一张原地更新的卡片里而不是连发新消息，完成后删掉卡片，再用正常消息发结果（[OpenClaw 流式文档](https://docs.openclaw.ai/concepts/streaming)）。Opus 5.5 有个坑：它在工具调用之间写的进度说明是以 `thinking` 块返回的，默认显示为空，只渲染 `text` 的客户端在长任务里看起来就像卡住了。解决办法是开启 `display: "updates"`（beta），或者由框架统计连续沉默的工具步数，达到 5 步左右时插一句"用户有一阵没听到你的消息了"；Anthropic 的测试显示后一种做法让长时间沉默的任务比例大约减半，成本没有变化（[Prompting Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)）。另外，Opus 5.5 的思考无法关闭，默认 effort 是 medium；在聊天产品里删掉"仔细思考再回答"这类句子，回复会更早开始，质量也没有明显下降。

## 对 3 天 demo 的具体设计建议

**架构保持一个制片人主线程。** 每个聊天线程对应一个 Agent SDK 会话，每轮恢复它。主线程负责所有对话和用户选择，可以把参考视频分析、视觉质检交给子 agent，但子 agent 的冗长输出不要进入聊天流。Grok Bot 101 讲的"外环 agent 保持干净上下文"就是这个意思。Seedance 封装成进程内 MCP 工具，提供 `seedance_submit` 和 `seedance_status` 两个接口：提交后立即返回任务 ID，由后台队列轮询，成功后立刻下载到本地磁盘。队列的并发上限要按账号实际配额来设，个人账号很可能只有 3 个，并且用 `execution_expires_after` 把卡住的任务控制在 1 到 2 小时内。代码渲染建议直接用 HyperFrames 的 skill 和 CLI，并在系统提示词里明确写出"使用 HyperFrames，遵守 seek 确定性约定"，否则 Opus 会自己手写引擎。不要用 Remotion，它在服务端的许可需要花钱。

**`project.json` 是唯一的真相源。** 字段至少包括画幅（默认 1080×1920、30 秒、中文）、`shots[]`（每个镜头有 `kind: code|gen`、起止时间、代码模板变量，或 Seedance 提示词、参考图、所选的那次生成及其哈希）、`overlays[]`（价格、卖点、CTA）、`vo[]`（按句生成，带逐字时间）、`music` 和 `captions`。每轮对话结束时保存一个版本快照，并记录 JSON-Patch 操作日志；这份日志同时就是项目 100 分档要求的轨迹记录。链路 2 的"再改改"就是新的 patch 加脏镜头重渲；链路 3 的字幕修改只动字幕轨，不触发任何生成调用，几十秒就能出新版。

**链路 1 的默认配方：代码打底，Seedance 点睛。** 一条 30 秒广告建议这样分配：代码负责钩子大字（0 到 3 秒）、卖点和价格卡、结尾品牌卡加 CTA；Seedance 负责 1 到 3 个 5 到 8 秒的使用场景或氛围空镜，提示词里写"无文字、无 Logo"，再由代码叠加文字。多段生成时把 `generate_audio` 关掉，整条片子只用一条口播加一条音乐，否则各段的声音会接不上。Seedance 的生成任务要在 agent 写代码镜头的同时并行提交，这样整体等待时间大致等于最慢的那一段生成。用户上传了产品图，就作为 `reference_image` 传入，并在提示词里写清角色，比如"@图像1 是产品"。及格线阶段可以跳过样片模式，直接出 720p 终版，以减少实现复杂度。等链路 2 需要频繁改镜头时，再接入 2.5 的样片模式或 2.0 fast 的 480p 预览。

**交付前先自检。** 渲染完成后用 ffmpeg 的 tile 滤镜拼两三张 4×4 联系表，交给 Claude 按"前 2 秒有没有钩子、手机尺寸下文字是否可读、品牌是否准确、产品有没有变形"打分，最多修 3 个最差问题再给用户看。一张 2576 像素以内的联系表约 4.8k token，每轮质检的成本不到 0.1 美元。再加上 ffmpeg 的 `blackdetect`、`freezedetect`、`silencedetect` 做信号层检查。

**对话层要专门投入时间。** 系统提示词用中文散文写，不要写成 Markdown 文档。人设是"像微信里一个靠谱的自由职业制片人"。点名禁止表格、标题、加粗小标题、编号选项菜单，以及"好的！以下是""希望对你有帮助"这类开头和结尾的套话。常规创意决定自己拍板并用半句话说明，需要提问时一次只问一个并带上推荐。提示词里放两三条正面示例，比如"收到，按竖屏快节奏剪个 30 秒的，两三分钟。"和"初版好了。结尾 logo 出来得有点晚，要的话我收紧一下。"闲聊和小改动用 low effort，规划分镜用 medium，并通过逐条消息设置 effort，这样不会让提示词缓存失效。前端要做到：消息一到就显示"正在输入"；一张原地更新的进度卡显示"脚本 ✓、分镜 ✓、生成镜头 2/3、合成中"；中间只在有可看的东西时插话，比如分镜静帧；完成消息先放视频，再配一两句话，最多提一个可以改的点。还可以给轨迹日志加一个"机器人味检测"：每条助手消息检查是否含 Markdown 表格、标题、超过一个问号、黑名单开头和结尾、单个气泡超过约 300 字，这样项目设想的 2×2 对比就有了可量化的指标。

**有意不做的部分。** 3 天内不做画布编辑器，用编号镜头配缩略图联系表代替，用户说"第 3 镜"就能指到具体镜头。不做数字人口播，因为 Seedance 不收真人脸参考，而且这不是及格线要求。链路 4 的爆款复刻留到后面，但现在就让分镜 schema 和参考分析的输出格式保持一致，以后只需要加一个"参考片转 `template.json`"的前置步骤。

## 结论

这轮调研最重要的发现是：项目对标的两个标杆，实际上分别对应我们要解决的两个独立问题，而这两个问题都主要是工程和提示词问题，跟模型选择关系不大。Claude Motion 和 Opus 5.5 的视频证明，用代码渲染广告里所有必须精确的部分是行业正解；Grok Bot 证明，"像真人"来自交互约定。Creatify 自测数据里"直接生成 3.65 到 3.85 分、加编排 1.90 分"的差距，以及 claude.ai 系统提示词不进入 API 这一事实，指向同一个结论：同样是 Opus 5.5 加 Seedance，做得好坏取决于框架这一层。

对 demo 而言，风险排序和直觉相反。最可能出问题的不是生成质量，而是 Seedance 的并发配额和排队时间、24 小时过期的结果链接，以及聊天在几分钟渲染期间显得"死掉"。这些都需要在第一天用真实账号测出来，不能只看文档。还有几件事没有定论：Seedance 2.5 当前的并发上限、API 端到端延迟的 p50 和 p95、BytePlus 对部署区域的限制，都只有二手或过期信息。Claude Motion 的时长上限和 Grok Agent Mode 的内部实现也没有官方文档。建议把这些当作 demo 第一天就要实测的待验证项。
